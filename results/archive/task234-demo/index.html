面向 AI Coding 的团队资产可感知复用系统 —— 任务二 / 三 / 四 交互演示

以 v2.0.x（TencentDB-Agent-Memory）+ MemoryProxy 注入管线为底座。系统须回答四个问题：资产是否真被使用（证据链）、用户能否理解资产如何影响结果（回执）、系统能否证明效果（反事实对比）、结果能否反哺团队资产（candidate 生命周期）。下方三个面板分别对应任务二（检索与最小上下文）、任务三（可信归因）、任务四（可感知回执）。

② 混合召回 + ③ 六维重排

core 混合检索召回 → 六维重排。重排权重：

相关性 0.40可信度 0.15历史效果 0.15新鲜度 0.10环境兼容性 0.10Token 成本 0.10
候选资产相关度六维加权重排后selected

口径（2026-09 对齐真实实现）：「相关度」= core /v3/skill/search score（当前 core 实现为 BM25，候选集内 min-max 归一化到 [0,1]；RRF 融合是 core 后续项，口径不变）；「六维加权」= 相关性×0.40 + 可信度×0.15 + 历史效果×0.15 + 新鲜度×0.10 + 环境兼容性×0.10 + Token成本×0.10。「selected」= 加权总分 ≥ 0.55 且名次 ≤ 5（双条件，与 config.yaml `selectedThreshold: 0.55` 一致）。被标记「筛选排除」的候选仅停留在 recalled，不会进入注入——这就是任务三证据链里 selected(decision="rerank") 的真实依据。

召回 ≠ 命中即有用。CodeRAG-Bench 实测：gold 文档显著提升 SWE-Bench 27.4%，但当前检索器对仓库级任务的**有用上下文召回率有限**——这正是任务二用「六维重排」而不是单纯提高 top-k 的原因。
Wang et al., CodeRAG-Bench, NAACL 2024

④ 预算约束下的最小上下文

只对「selected」集合裁剪。拖拽 Token 预算，观察最小但充分的上下文如何形成（避免把大量无关历史直接注入）。

4,000
长上下文不是免费的。RULER 实证：广告宣称的上下文窗口远大于「有效上下文长度」（Gemini 1.5 Pro 宣称 1M / 有效 128K；GPT-4 宣称 128K / 有效 64K）。「Lost in the Middle」位置偏置 + 纯长度退化（FLenQA：0.92 → 0.68@3k tokens）意味着：注入越多越靠中部，越难被真正用上。
Hsieh et al. RULER, 2024 · Levy et al. FLenQA, ACL 2024

资产使用证据链：recalled → selected → injected → used → validated → corrected → contributed

任务三要求区分各环节并建立 asset → decision/change → outcome 关联。点击每个环节查看：当前 v2 状态、缺失的证据类型、记录方案。核心立场：「被召回/被注入」永远不等于「被使用」，「被使用」不等于「产生正效果」——每一环都要有独立于模型自述的结构化证据。

召回率 83.5%，但采用率只有 47.9%。把检索覆盖与 LLM 实际利用分开测量：237 个应被使用的实体里模型只取到 136 个。这正是任务三要补的「selected / used」证据——只有工具调用、代码 diff、测试结果能证明「真的用了」。
Separating retrieval coverage from LLM utilization, ACL 2026

用户可感知的资产使用回执 由 asset_event 事件表聚合生成，非 LLM 自述

会话内执行 mem:receipt（或任务收尾自动追加）输出摘要；点开每张资产卡查看：名称/类型/来源/版本/更新时间/验证状态/使用位置/为什么适用/对应代码修改与测试/风险标记。回执回答任务四的五个问题：用了哪些资产、什么类型、影响了哪个决策、为什么适用、存在哪些版本/时效/权限/环境兼容性风险。
